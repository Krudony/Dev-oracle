# Session Retrospective: Teamwork Preview, Live AiPASS, and Claude Reliability

**Session date:** 2026-09-04  
**Focus:** Turn `teamwork-preview` from a misleading demo into a usable live AiPASS document-analysis application.

## Session Summary

The team built and repaired a Thai official-document explainer at `teamwork-preview`, connected it to the local AiPASS Bridge, exposed real model selection, removed misleading sample-output behavior, hardened upload and streaming behavior, and resolved Claude document-reading failures. The final service is running locally at `http://127.0.0.1:8788`, with one attached AiPASS extension and live readiness confirmed. ## AI Diary

I began this session with a product that technically rendered but did not yet deserve the user's trust. The hardest feedback was also the most useful: the interface looked poor, the output did not match the uploaded document, and the system claimed AiPASS behavior while surfacing canned tax content. I felt the gap between “the server responds” and “the product is real” very clearly. It forced me to stop treating readiness checks as proof of correct user experience. I had to trace provenance from the chosen file and model all the way into the live request, then make stale state impossible to mistake for a fresh analysis. The Claude failure was another important correction. A generic error looked like a model incompatibility, but the evidence showed both Claude Sonnet and Opus worked; the real document prompt simply needed longer than the application's arbitrary 30-second wall clock. Seeing the real Opus request finish in 45.8 seconds made the failure mode obvious. I am satisfied that the final fix was not just “increase a number”: changing the limit to idle semantics better matches streaming systems and lets productive long responses continue. The repeated independent reviews also helped turn sharp user criticism into concrete reliability work rather than cosmetic reassurance.

## Honest Feedback

Three friction points dominated this session. First, the initial implementation allowed demo output and live output to coexist too ambiguously. That was a product-design failure, not merely a UI bug: when users upload a document, any canned result that survives on screen destroys confidence immediately. Second, the first readiness claims were too infrastructure-centric. A healthy bridge, signed-in extension, and successful short round trip did not prove that the full document workflow used the selected model or displayed document-specific content. We needed payload capture, browser-state checks, and real prompt tests earlier. Third, debugging was lengthened by treating the 30-second timeout as a reasonable universal default. Reasoning-heavy models have very different first-token latency, so total-duration timers are a poor fit for SSE. The team eventually corrected all three issues, but the workflow would have been calmer and faster if provenance, live-only defaults, and slow-model behavior had been explicit acceptance criteria from the first implementation pass.

## Lessons Learned

- Readiness is layered: bridge health, extension count, authentication, model catalog, request payload, streamed response, and UI provenance must all agree.
- Never let demo output look like analysis of a user-selected file; bind every visible result to the exact input and execution mode that produced it.
- Clear results immediately when document, text, or model inputs change, including while asynchronous file reads are pending.
- For streamed AI work, measure inactivity rather than total elapsed time. Reset the idle deadline on meaningful text or reasoning events.
- Test the actual slow model and realistic prompt. A tiny round-trip probe cannot validate document-processing latency.
- Keep exactly one browser extension attached when the bridge duplicates deltas per connected client.
- A trustworthy handoff includes a running service, cache-safe assets, automated regression tests, and an independent reviewer—not only implementation notes.
